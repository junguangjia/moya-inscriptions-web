## 1. Owner decisions

Step one (Issue #384) listed "Linking user posts to entries" as a non-goal and
showed no upload call to action, because no link between a post and an entry
existed yet. The step-two plan put three choices to the Owner, each with a
recommendation. The Owner answered on 2026-11-07:

> 可以，按照推荐吧

So the recommended option of each choice is decided:

1. **D1 = A.** The rows that open Catalog Detail get a 帖子 section
   with「上传这件碑帖」 in Catalog Detail, before the discussion, built from the
   same parts as the 词条卡.
2. **D2 = A.** A post is attached to at most one entry: one row per work.
3. **D3 = A.** An attachment takes effect at once. The AI or the Owner can take
   it off through the Admin MCP, and reports work as before; the post's own
   moderation applies as today.

Earlier Owner rules that stand: a post's image never replaces a missing Catalog
image on the timeline; no 「暂无」-style absence wording; the timeline stays
clean.

Settled by the agent under those decisions. These are design choices, not the
Owner's words, and the signature confirms them:

1. A post is an existing work. A new table associates it with an entry, as
   `community.thread_works` does for Threads; the works table and its grants
   stay as they are.
2. An author takes a post off by detaching it. An operator takes one off by
   withholding it, and the row records the entry it was withheld from
   (`withheld_entry_id`). That record blocks an author re-attach to that entry
   only: its author may attach the post to any other entry. Only the most recent
   withhold is remembered. An operator attach to that entry lifts the withhold.
3. Everything a viewer sees about posts comes from new routes, so no existing
   strict response gains a field and `GET /v1/community/timeline` is unchanged.
   One route answers "which entry" for both a work and a Catalog record. There
   is no batch route for an 「已在」 mark: 「关联我发过的帖子」 checks each pick
   when it is chosen and asks before a move.
4. Each viewer's post count is the length of the post list that viewer sees, and
   a work's entry is read by the same rule: its author reads it for an own work
   the list shows them, one an operator hid or removed included, so a hidden
   post can be taken off; a third party only for a public work. The operator
   counts include public posts only, the same for the Owner and the AI.
5. Two ops, both on tools that exist: one read and one reversible write. Nothing
   irreversible is built, and no post or association row is ever deleted.
6. The import refuses a file that drops a row holding attached posts, with
   counts only. The refusal runs after the replacement, inside the import's
   transaction, so nothing changes and no author attach can slip in between. A
   work's permanent deletion, by its author, by an account purge or by the
   recycle bin's purge, detaches its attached row in the same transaction, so an
   erased post is never counted.
7. Every writer of the new table locks the work, then the entry, then the post
   row, and an attach that waited for the import locks its entry again after it.
   No pair of writers deadlocks, and each race ends as one of its two serial
   orders.
8. 「上传这件碑帖」 reaching an unfinished new-work session sets that
   session's 关联词条 to the tapped entry and keeps the rest of the draft. The
   tap is spent once applied: a reload, Back then Forward,
   or 返回正在编辑的作品 never applies it again. The Thread quick composer
   (参与话题) offers no 关联词条 and never sends an entry; a tap that finds an
   unfinished Thread post shows 「还有一项编辑没有结束」, as any other open edit
   does, so the entry is never dropped unseen. The author's own posts that
   others cannot see carry the profile works grid's mark in the posts grid.

Not decided here: the release day. That stays a later Owner gate.

## 4. Migration approved (Constitution section 17, item 3)

Community `20261107010000_timeline_entry_posts.sql`, additive:
`community.timeline_entry_posts` with `work_id` (primary key, references
`community.works`), `entry_id` (references `community.timeline_entries`,
`DEFERRABLE INITIALLY DEFERRED`, no action on delete), `state` (`attached`,
`detached` or `withheld`, default `attached`), `withheld_entry_id` (a plain id,
not a key), `attached_by` and `updated_by` (`author`, `owner` or `ai-admin`),
`version` (default 1, at least 1), `attached_at` and `updated_at` (default
`now()`). Checks: `entry_id` is set exactly while the row is attached; a
withheld row records the entry it was withheld from; that id has the entry id's
shape. One partial index on `(entry_id, attached_at DESC, work_id DESC)` where
the row is attached. The grants in `grant-runtime.sql` are those in section 2,
in blocks that skip an earlier phase without the table, with a revoke of any
table-level `INSERT` or `UPDATE` first.

`scripts/import-timeline.mjs` keeps `TIMELINE_MIGRATION_ID`. It checks that the
new table exists before it counts posts, so it still runs on a database the new
migration has not reached.

Once merged, a further change is a new additive migration. A new operator label,
or more than one entry per post, needs one.

No other migration is approved.

## 5. Deferred

- More than one entry per post (D2 option B): an additive migration that changes
  the primary key, and a picker with several choices.
- Review of each attachment before it shows (D3 options B and C): a new queue
  op.
- Telling an author that an operator took a post off. The author
  sees 收录于 disappear.
- A batch read of which entry each of my works is on, for
  an 「已在：某词条」mark in the list of my works: not built, by decision. The
  picker checks each pick when it is chosen and asks before a move.
- Post counts on group members and on shelf entries, which the design did not
  draw.
- Remembering every entry a post was withheld from; the row keeps the latest.
- A `timeline_post` record type for `admin_find` and `admin_get`: after the S10
  record descriptors. `read-timeline-posts` filters by work, entry and author.
- Hard delete of a timeline row: still #355 S8b, and it must handle attached
  posts, as section 2 states.

A rollback is not just a return of the runtimes. The previous Backend parses
stored draft content strictly, so a draft saved with 关联词条, and the history
of any draft or edit whose lineage holds such a snapshot, would fail to open.
Before the runtimes return, the key is taken out of stored drafts and their
history once; those drafts lose their chosen entry. The previous release does
not detach a deleted work's post, so once this release runs again, the rows of
works deleted in between are detached once. The design doc's release section
holds both statements.
