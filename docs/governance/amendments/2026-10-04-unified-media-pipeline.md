## 1. Scope

The Owner instruction replaces the test-stage media implementation with one
coherent pipeline: one asset/rendition/reference model, private source and
master storage, bounded asynchronous sandboxed processing, versioned
role-appropriate renditions, direct uploads, published delivery through the
Owner's existing Tencent Cloud EdgeOne subscription and deep zoom in the
existing Web Viewer. Each increment is merged PRs, a Production deployment, a
real acceptance run and a recorded rollback point.

1. **Pipeline.** PR 1a (not user-visible): rendition model, central versioned
   recipes with a bounded `viewer` role, a separately supervised media worker, a
   no-network sandbox for all untrusted decoding and rendering, Catalog
   processing on the common pipeline, and the retention hold. PR 1b
   (user-visible): additive rendition candidates and placeholder colour in the
   API, responsive Web images and a progressive Viewer, served through the
   existing authorized read paths.
2. **Published delivery.** A dedicated private published origin behind a new
   project-specific media hostname served by the existing EdgeOne subscription
   (one provider; no multi-provider layer); publication and withdrawal with
   EdgeOne purge; public reads switched by configuration.
3. **Uploads and profile imagery.** Direct browser-to-storage upload switched by
   configuration; avatar and background imagery moved out of PostgreSQL into the
   pipeline.
4. **Deep zoom and completion.** IIIF Image API 3 Level 0 JPEG tiles inside the
   existing Viewer, resolution-policy controls, backfill, before/after
   measurement, retirement of superseded paths and of the old media hostname,
   and the recorded retention follow-up.

Production media changes (migrations, backfills, byte extraction, a
write-capable worker and behaviour-changing deployments) follow the recorded
handoff of the separate PostgreSQL 16 migration task, which owns that database
move and its rollback; every migration of this task must pass on PostgreSQL 16.

Not authorized: Apple or HarmonyOS work; AVIF or extra decoders as completion
dependencies; a dynamic image server, message broker, microservice platform or
cloud migration; prepaid packages, instance changes or new paid products (the
already purchased EdgeOne subscription is the only exception); any change to the
old Pilot storage or, before increment 4, to the existing media hostname;
deletion of pre-existing data inside the retention window (entry 13).

## 3. Owner decisions recorded

The Owner answered the batched questions on 2026-10-04 (Issue #206 r2) and
continued the instruction the same day (r3):

- **Constitution §19 and ADR 0003:** approved as entries 10 and 11, in effect.
- **Public resolution:** long scrolls (long edge above 2.5 times the short edge)
  keep today's short-edge-aware bounds (`full` at most 16,000 px on the long
  edge and 40 MP; `display` at most 1,280 px on the short edge and 20 MP) as
  both the existing-work limit and the new-work default; every other image uses
  8,192 px on the long edge. Public `full` appears in detail contexts within
  these bounds, and the authorized relay applies the same rule.
- **Cloud identity for increments 2 and 3:** approved as proposed. Two new
  keyless roles, one for publishing (writing and deleting only the published
  origin's task paths, and creating and reading EdgeOne purge tasks, with the
  application refusing any purge target outside the new media hostname) and one
  for short-lived upload credentials limited to one staging object, each
  assumable only by the existing publishing identity, which may assume exactly
  those two; a certificate permission for the new hostname only if certificate
  renewal cannot deploy itself. No new long-lived keys; this delta and the
  published origin's read-only access statement for EdgeOne are the ceiling.
- **Retention:** only task-initiated deletions are held (entry 13).
- **Delivery provider and sequencing:** increment 2 uses the existing EdgeOne
  subscription (section 1); production media changes wait for the PostgreSQL 16
  migration task's handoff (section 1). The new media hostname gets no public
  DNS record and public reads are not switched until publication and withdrawal,
  including the purge, pass acceptance on a warmed edge.

## 4. What stays as it was

- The Constitution and every other non-conflicting active amendment.
- No dependency upgrade. Any new dependency, such as a deep-zoom viewer library
  in increment 4, needs explicit scope approval.
- Production domains, delivery configuration and credentials are never
  committed; the published-media origin is configured privately at runtime.
- Public contracts change additively. Content IDs, crop intent, Live Photo
  playback, publication and moderation rules, draft privacy, upload limits,
  quality modes and capacity accounting stay as they are.
- Existing Catalog keys are never renamed or rewritten. PostgreSQL holds
  metadata and relationships, not new image byte payloads.
- Independent exact-head review and every applicable Owner gate per increment.

This amendment records authorization and boundaries. It does not record the
completion or Production acceptance of any increment.
